# Первая публичная alpha: локализация и распространение

Дата: 2026-09-09. [English](2026-09-09-alpha-localization.en.md).

Это исследованное предложение, а не объявление релиза и не утверждение, что перечисленные возможности уже реализованы. Исходная версия: `8adbe8e`.

## Текущее состояние

- Работающие адаптеры приложения есть только для Windows. Проверка независимого ядра в Linux CI не означает наличие готового Linux-приложения.
- Приложение наблюдает за языком ввода; раскладку переключает Windows или активная программа.
- `switcher-windows/src/layout_monitor/snapshot.rs::language_for` получает язык из HKL через `LCIDToLocaleName`. Этот код не ограничен русским и английским.
- В `switcher-core/src/content.rs` отдельные цвета и звуки заданы для RU/EN, для остальных распознанных языков используются нейтральные. Сейчас бейдж берёт первые два символа основного языкового тега. Перед заявлением расширенной поддержки следует сохранять целые двух- и трёхбуквенные коды: например, обрезка `fil` до `FI` создаёт обозначение, похожее на финский язык.
- Региональные варианты пока имеют одинаковое обозначение языка. Режимы IME, например прямой ввод и хирагана в японском, не являются проверенной возможностью.
- Конфиг принимает `ui_language = "ru"` и `"en"`, но строки меню и состояния пока записаны в коде на русском. Принятие английского значения в конфиге не означает работающий английский интерфейс.

[Документация Microsoft по HKL](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeyboardlayout) описывает идентификатор языка ввода, который может соответствовать и IME. Поэтому обещание универсальной поддержки IME потребовало бы отдельных проверок.

## Варианты локализации в Rust

| Подход | Преимущества | Затраты и применимость |
| --- | --- | --- |
| Fluent с `fluent-bundle` | Грамматика в переводах, множественное число, варианты, именованные параметры, изоляция направления текста; контроль загруженных каталогов | Нужна небольшая оболочка приложения для поиска переводов и fallback. Рекомендуется для расширяемого нативного интерфейса. |
| `rust-i18n` | Встроенные каталоги YAML/JSON/TOML, удобный макрос, резервные локали | Подходящая более простая альтернатива; глобальное состояние языка и её API отличаются от текущей архитектуры с каналами. |
| Ручные таблицы строк в Rust | Минимум начальных зависимостей | Каждый язык увеличивает код приложения; грамматику, параметры и инструменты перевода придётся развивать отдельно. Плохо соответствует запросу на дальнейшее расширение. |

Первичные источники: [Project Fluent](https://projectfluent.org/), [fluent-bundle](https://docs.rs/fluent-bundle/latest/fluent_bundle/), [rust-i18n](https://docs.rs/rust-i18n/latest/rust_i18n/). Альтернатива небольшой собственной оболочке выбора ресурсов — [встроенный загрузчик fluent-templates](https://docs.rs/fluent-templates/latest/fluent_templates/).

## Предлагаемое поведение приложения

1. Собрать идентификаторы языков, их названия на родном языке и встроенные `.ftl`-каталоги в модуле локализации приложения. Хранить переводы отдельно от Rust-кода. При прямой работе с bundle загружать выбранный язык и резервный английский.
2. Использовать языковые идентификаторы Unicode с регионами и письменностями, когда они нужны. Для [разбора и нормализации](https://docs.rs/unic-langid/latest/unic_langid/) подходит `unic-langid`; произвольная обрезка строк не заменяет подбор локали.
3. Добавить в трей `Язык -> Как в системе / English / Русский / ...`; использовать названия языков на них самих. Выбор сразу меняет меню, подсказку и состояние, сохраняется в конфиге. Язык интерфейса независим от языка ввода.
4. Для режима «Как в системе» брать предпочтения языка интерфейса Windows, а не раскладку или региональные форматы дат. Windows-адаптер вызывает [GetUserPreferredUILanguages](https://learn.microsoft.com/en-us/windows/win32/api/winnls/nf-winnls-getuserpreferreduilanguages), оболочка получает обычные строки через платформенную границу.
5. Подбирать доступный вариант локали; при неподдерживаемом языке или отсутствующей строке использовать английский. Регистрация доступных языков централизована: новый каталог не требует правок по всему трею.
6. Сохранять существующий явный выбор и остальные настройки. Для новых установок — режим «Как в системе». Диагностические коды и логи разработчика остаются стабильными; пользовательские описания переводятся.
7. В CI проверять каждый каталог: синтаксис, повторяющиеся и пропущенные ID, совместимость параметров, ошибки форматирования, fallback и выбор локалей. Отдельно проверять смену языка интерфейса и сохранение настройки, независимо от смены раскладки.
8. Сохранять корректный Unicode и изоляцию направления текста Fluent. При добавлении RTL-языка понадобится проверка нативного меню: одна библиотека переводов не подтверждает правильную RTL-компоновку.

Предложенный начальный набор интерфейса: русский, английский, немецкий, испанский, французский, бразильский португальский; окончательный набор выбирает пользователь. Документация на русском и английском с возможностью расширения уже запрошена.

## Предложение по установщику и выпуску

Выпустить `v0.1.0-alpha.1` как GitHub prerelease: скачиваемый Windows-установщик, portable ZIP, SHA-256 и описание изменений на RU/EN. Предложенная первая платформа — Windows 11 x64; расширение списка Windows и архитектур требует определения объёма и проверки.

Для установщика использовать [Inno Setup](https://jrsoftware.org/isinfo.php). Он поддерживает Unicode, несколько языков, удаление и установку для текущего пользователя. Его [лицензия](https://jrsoftware.org/files/is/license.txt) разрешает распространение при соблюдении указанных условий; уведомления штатного установщика сохраняются. WiX подходит для MSI, но перед его выбором нужно учитывать текущие [условия maintenance fee](https://docs.firegiant.com/wix/osmf/) и дополнительную сложность упаковки. Для первой пользовательской alpha MSI не обязателен.

Предлагаемое поведение установки:

- Постоянный каталог приложения текущего пользователя, `PrivilegesRequired=lowest`, без запроса прав администратора.
- Ярлык в меню «Пуск» и запись удаления. Автозапуск остаётся опцией трея.
- Обновление сохраняет конфиг. Удаление убирает файлы приложения и относящуюся к нему запись автозапуска, не затрагивая чужие файлы и значения реестра. Пользовательские данные по умолчанию сохраняются.
- Обычный запуск защищён от второй копии. Именованный mutex также проверяется установщиком перед обновлением и удалением работающего приложения. Явно изолированные диагностические запуски учитываются отдельно. Этот контракт описан в [Inno Setup AppMutex](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm).
- Сборка явно выбирает Windows MSVC; включает версию/manifest, сторонние лицензии и проверки установки, запуска, обновления и удаления в CI. Проверка пользователем на чистой Windows дополняет то, что не устанавливают hosted runners.
- Артефакты собираются из фиксированного коммита закреплёнными инструментами. До загрузки в draft release проходят форматирование, линтер, тесты, проверка зависимостей/секретов и установщика. Готовый draft публикуется как prerelease. [Документация GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

Репозиторий пока приватный. Есть четыре старых последовательных PR, релизов нет. Публикация должна представить собранную alpha в `main` после успешных проверок и привести старые PR в соответствие с результатом. До открытия доступа нужен выбор пользователя о личном email в истории; история не переписывалась.

## Запрошенные решения пользователя

- Начальный набор языков интерфейса.
- Поддерживаемые Windows и архитектуры процессора.
- Сохранение или скрытие существующего email в Git-метаданных.
- Двуязычность только основных публичных руководств на первом шаге либо также всех исторических исследований и ADR.
- Наличие подписи Windows-приложений либо допустимость неподписанной первой alpha.

Эти решения определяют объём выпуска. В рамках исследования не реализовывались установщик и локализация, не изменялась видимость, не выполнялись push, merge и публикация релиза.
