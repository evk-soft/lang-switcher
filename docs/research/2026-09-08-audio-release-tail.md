# Остаточная потеря короткого звука устранена запасом тишины перед закрытием

Дата: 2026-09-08. Windows 11 Enterprise 10.0.26200, Realtek Speakers,
Rust 1.96.1 / MSRV 1.87. Работа в текущей папке, без worktree.

## Пользовательский прогон полного приложения

Пользователь сообщил: при снятой резервной галке бейдж не меняет язык, при
включённой работает; снятая галка сохраняется после выхода и перезапуска.
Звук при сменах отсутствует, иногда слышен при переходе между программами.
Это подтверждает управление резервным путём, но не приёмку звука.

Каталог `target/fallback-manual-20260908-204102570`, исходная сборка `1dbf467`:
первый запуск 17:41:02–17:47:42 UTC завершён штатно. В нём **33 старта,
33 достижения clock и 33 освобождения** аудиопотока. PCM 3969 кадров, peak
12268/12321, клиент capacity=1036, GetStreamLatency=0. Clock доходит до
7938/88200 = 90 мс. Realtek выбран, endpoint 0,7/unmuted, session 1,0/unmuted.
Значит, отсутствие звука нельзя объяснить только непоступившим PlaySound или mute.

Лог показывает выключение fallback в 17:43:39 и включение в 17:44:17, затем
повторную пару off/on и выключение перед выходом. Run JSON нового запуска
17:47:48 содержит `fallback_enabled=false`; в 17:47:55 опция включена обратно.
Звук отдельно выключался с 17:45:59 до 17:46:14: отсутствие сигналов именно
в этом промежутке ожидаемо. Анализатор: `target/analyze-fallback-audio.py`.

## Различающий эксперимент

Все три случая используют один и тот же production Burst напрямую, одинаковые
90 мс исходного RU PCM и прежнюю громкость. Длительные диагностические данные
обходят только публичный лимит PCM/worker; сравнение E/B/C не меняет путь вызова.
WAV содержит входной PCM, не запись звука с устройства.

`target/audio-tail-live-20260908-205436771`:

| Случай | Содержимое | Endpoint peak до / во время / после | Ответ пользователя |
|---|---|---|---|
| E, №1 | 90 мс | 0 / 0 / 0 | «Нет» |
| B, №2 | те же 90 мс + 1 с нулей | 0 / 0,469416 / 0 | «Да» |
| C, №3 | 1 с нулей + те же 90 мс + 1 с нулей | 0 / 0,483150 / 0 | «Да» |

Все процессы exit 0, stderr пуст. E достиг 7938/88200, несмотря на нулевой
выходной уровень и отсутствие слышимости. Это опровергает достаточность
прежнего критерия завершения для данного устройства. Конкретный механизм
внутри Windows/конвертера/эффектов/драйвера не установлен; не следует
приписывать сбой конкретному APO или обещать универсальный тайминг.

В `target/audio-tail-20260908-205219771` проверены файлы E/B/C через Python wave:
PCM16 mono 44100, 3969/48069/92169 кадров. Короткие данные побайтово одинаковы,
отличия — только нули перед/после. PrepareOnly не запускал аудио.

## Выбор меньшего запаса

Первый sweep `target/audio-tail-sweep-20260908-205852841` содержал фоновый
звук (baseline 0,033–0,168) и исключён из обоснования. После просьбы остановить
музыку/видео пользователь подтвердил тишину.

Чистый sweep **до изменения production**:
`target/audio-tail-sweep-20260908-210121032`, два запуска каждого варианта,
нулевой baseline во всех случаях:

| Дописано после сигнала | Peak во время/после, повтор 1 | Повтор 2 |
|---|---:|---:|
| 0 мс | 0 | 0,000206 |
| 25 мс | 0,469416 | 0,469416 |
| 50 мс | 0,504833 | 0,469416 |
| 100 мс | 0,469416 | 0,515781 |
| 200 мс | 0,469416 | 0,469416 |

Измеритель относится ко всему endpoint, не к отдельной сессии и не к
акустической записи. Нулевой baseline поддерживает сравнение; окончательное
подтверждение слышимости получено отдельно от пользователя.

По [ADR-0020](../architecture/adr/0020-bounded-audio-release-tail.md) выбран
100-мс запас: больше проверенного нижнего значения 25 мс, существенно короче
секундного контроля. Это эмпирический запас совместимости. При ненулевой
сообщённой задержке берётся `max(100 мс, GetStreamLatency)`, округление вверх.
Пустой startup probe не дополняется. Clock ждёт весь буфер; в простое клиент
закрыт. Последующая ожидающая подсказка может задержаться ещё на 100 мс
из-за прежнего последовательного worker; latest-slot не создаёт длинной очереди.

В новом audio_compare T0..T1000 — **дополнительные** нули сверх production-хвоста.
T0 новой сборки уже не является отрицательным контролем без запаса. Скрипт
`scripts/check-audio-tail.ps1` сохраняет hash бинарника и ответы по E/B/C;
исторический sweep не переименован в результаты новой версии.

## Проверка исправления

Две регрессии сначала упали на прежней формуле, вынесенной без изменения
поведения в `render_buffer`: конец 90 мс считался финальным; минимум запаса
при нулевой latency отсутствовал. После исправления проверены исходные
отсчёты, нулевой хвост, clock для 190 мс, большая latency с округлением и
пустой probe. Clock, RAII, mailbox и watchdog не переписывались.
