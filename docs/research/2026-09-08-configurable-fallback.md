# Настраиваемая резервная проверка раскладки

Дата: 2026-09-08. Windows 11 Enterprise 10.0.26200, Rust stable 1.96.1,
MSRV 1.87.0, ветка `feat/m1-windows-mvp`, работа без worktree.

## Проблема и изменение

Прежняя политика снимала резервный таймер в обычных Win32-окнах независимо от
реальной доставки Shell/TSF. Это оставляло приложение без повторного чтения при
наблюдавшейся недоставке уведомлений. Пользователь разрешил период 200 мс и
попросил переключение из трея. Решение принято в
[ADR-0019](../architecture/adr/0019-configurable-layout-fallback.md).

Галка «Резервная проверка раскладки» по умолчанию установлена. Меняет
`[layout] fallback_enabled`, применяется без перезапуска и сохраняется. Старые
конфиги получают true; сохранённый false передаётся при создании адаптера,
не вызывая краткого включения. Выключение снимает и прежний резервный путь
Terminal/elevated; события Windows продолжают поступать.

При включении таймер работает для любого валидного чужого foreground. Если
foreground hook доступен, собственное/отсутствующее окно снимает таймер. При
отказе hook таймер помогает обнаружить новое окно, но не читает HKL собственного
или нулевого TID. Process/package probes удалены из частого пути. Контроллер
хранит последнее предпочтение между рестартами и отзывает wake до выхода потока.
Runtime не принимает уже отложенный ForegroundPoll после выключения опции.

Независимое ревью обнаружило отдельную гонку: открытие tray активирует наше
служебное окно, и отложенное событие могло подменить раскладку редактора нашей.
Общий reader теперь проверяет PID и возвращает специальную паузу. Runtime
сохраняет последнюю раскладку без звука и предупреждения. Повторное ревью
подтвердило закрытие замечания; новых замечаний не осталось. Workflow
`rust-adversarial-review` в среде недоступен, использовано независимое ревью
существующим агентом без изменения им native-файлов.

## Автоматическая проверка

- RED политики: обычный чужой foreground возвращал Disarm вместо Arm;
  собственное окно оставляло Keep вместо Disarm. Оба теста сначала падали
  на утверждениях. Для новой модели config/engine RED был ошибкой компиляции
  отсутствующих типов/вариантов; runtime проверялся после подключения порта.
- RED гонки собственного окна: reader принимал собственный HKL, runtime
  показывал предупреждение вместо тихой паузы. Оба новых теста сначала падали,
  затем прошли с исправлением.
- GREEN: 40 app + 61 core + 3 platform + 65 Windows + 9 в audio comparison
  example + 1 в overlay example = **179 исполнений тестов**, 0 failures.
  Девять аудиотестов подключены также из примера; это 170 без повторного включения.
- Native-тест реально взводит SetTimer, получает WM_TIMER, выключает опцию
  перед потреблением отложенного тика, снимает таймер и подтверждает отсутствие
  новых WM_TIMER в течение 500 мс, затем включает снова. Проверяет и случай
  отсутствия обоих уведомляющих hooks; чужие окна не активируются.
- `cargo fmt --all -- --check`, Clippy workspace/all-targets с `-D warnings`,
  `cargo test --workspace --all-targets`,
  `cargo +1.87.0 check --workspace --all-targets --locked` — exit 0.
- Release приложения и Windows examples собраны. Журнал:
  `target/verification-configurable-fallback-final.txt`.

Артефакты: `target/fallback-resources-20260908-143944879/metrics.json`,
`false/samples.json`, `true/samples.json`, отдельные config/logs/stderr.
Измеритель: `target/measure-fallback.ps1`. Бинарник **2 895 872 байта**,
SHA-256 `8F6816B786E501009BAF66AA95B2B293FBE24B02C5A8EB585D7C18F0837B33B1`.

Два последовательных запуска с `--run-for 90`, сначала false, затем true.
Sound=false, INFO, transient по умолчанию. 24 логических процессора; после

В false нет взведения резервного таймера. В true лог подтверждает период 200 мс

это наблюдение рабочего desktop, **не строгий простой** и не контролируемая

Кроме известных startup-предупреждений caret M2 и неподтверждённой доставки
Shell/TSF новых WARN/ERROR в этих запусках нет.

## Следующий пользовательский контроль

`scripts/start-fallback-check.ps1` запускает полное приложение с постоянным
бейджем/звуком и независимый Win32 `layout_probe --sample` на 10 минут.
Новый каталог изолирован от обычных настроек; `-DataDir` использует сохранённый
конфиг для проверки перезапуска. `-PrepareOnly` не запускает процессы.
PowerShell parser прошёл; `-PrepareOnly` проверен для нового каталога и
повторного использования того же каталога, hash config не изменился.
Ревью скрипта выявило экранирование конечного `\` в `-DataDir`; исправлено
добавлением компонента `.` к каталогу до упаковки аргумента. Передача через
реальный Start-Process проверена на обычном пути с конечным slash, пути с
пробелами, drive root и UNC root: дочерний Python получил четыре ожидаемых
аргумента без склейки. Замечание закрыто повторным ревью.
Пошаговая матрица on/off, сохранения, Notepad++/Terminal и обычной Win32-fixture —
в [smoke-чеклисте](../smoke/m1-windows.md).

200 мс — номинальный период WM_TIMER, а не гарантия задержки. Быстрый A→B→A
между чтениями может быть пропущен. Прежний эксперимент Terminal с адресным
TSF getter не доказывает работу полного приложения или отдельного обычного
Win32-reader: возможное влияние getter не исключено. Причина старых пропусков
Terminal отдельно не установлена. Ручной контроль новой сборки, слышимость при
реальной смене, DPI/прочие классы окон и полный M1 остаются открытыми.
