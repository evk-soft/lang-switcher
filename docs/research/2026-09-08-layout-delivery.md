# RU/EN: приложение пропустило переключения в активном тестовом окне

Дата: 2026-09-08. Windows 11 Enterprise 10.0.26200, release приложения из
`47e51f3`. Основная папка проекта, без worktree. Исправления аудио/трея/памяти
и их проверки описаны в [предыдущем отчёте](2026-09-08-idle-fixes.md).

## Результат

**Приёмка доставки RU/EN не прошла.** Внешнее Win32-окно `layout_driver`
выполнило 20 принятых Windows смен HKL, сохраняя foreground. Приложение
не записало ни одного чтения раскладки или старта аудио в этом интервале.
Это блокер M1. Корневая причина пока не установлена; нельзя считать доказанным
ни дефект конкретного API Windows, ни необходимость постоянного опроса.

## Первый прогон: 07:40 UTC

После согласия пользователя fixture запущена с `Start-Process -WindowStyle Normal`.
Приложение работало 55 секунд с отдельным конфигом: DEBUG, sound.enabled=true,
volume=0.08. Fixture меняла только собственный поток через
WM_INPUTLANGCHANGEREQUEST; клавиши в сторонние окна не посылались.

| Наблюдение | Результат |
|---|---|
| Принятые изменения собственного HKL | 20/20, попеременно 0x4090409 и 0x4190419 |
| Запросы | 07:40:40.288–07:40:51.782 UTC, интервал около 600 мс |
| Приём нового HKL самим окном | 4–7 мс; это не latency приложения |
| Чтения раскладки приложением между первым запросом и окончанием цикла | 0 |
| Shell/TSF | ни одного подтверждения доставки; capabilities остались Degraded |
| Резервный опрос | отключён в 07:40:40.536 при обычном Win32 foreground |
| Аудио в интервале переключений | нет `audio stream started` |
| Завершение приложения | в 07:41:22.540, `clean=true`, stderr пуст |

Проверка GetForegroundWindow перед каждым переключением не сообщила потери
фокуса. После возврата в другие окна приложение снова читало раскладку по
ForegroundChange; отдельный звук возник только в 07:40:56.107, после теста.
Это не подтверждение доставки тестовых 20 смен.

PowerShell-обёртка ошибочно ждала приложение лишь 20 секунд после завершения
fixture и выдала свой timeout раньше его 55-секундного срока. Поэтому exit code
первого приложения/fixture обёрткой не сохранён. Собственный журнал приложения
подтверждает последующее штатное завершение; timeout обёртки не выдаётся за crash.
В следующем запуске ожидание обёртки исправлено.

Артефакты: `target/m1-manual-visible-20260908-104027/driver.txt`,
`driver-error.txt`, `stderr.txt`, `logs/lang-switcher.2026-09-08.log`.

## Диагностика получателя Shell: 07:44 UTC

Добавлен `cargo run --release -p switcher-windows --example shell_probe -- 55`.
Он регистрирует два собственных скрытых окна: message-only, как у приложения,
и обычное top-level. Полученные сообщения пишет в stdout без чтения чужой памяти.
Подписки снимаются до уничтожения окон. Окна не показываются и не меняют фокус.
stdout нужно направлять в файл или непрерывно читать. Ограничение длительности
1–120 секунд и drain до 128 сообщений не относятся к коду резидентного приложения.

В 55-секундном прогоне оба RegisterShellHookWindow вернули true; каждый
получатель получил **553 сообщения с одинаковым распределением**:

| wParam | На каждое окно |
|---|---:|
| 1 | 4 |
| 2 | 122 |
| 4 | 8 |
| 5 | 1 |
| 6 | 237 |
| 16 | 107 |
| 53 | 9 |
| 54 | 9 |
| 32774 | 56 |

Это подтверждает реальную работу подписок обоих типов. Значения без описанного
контракта остаются числами, им не приписывается семантика смены языка.
**Fixture этого второго прогона не получила foreground и завершилась до первой
смены.** Отсутствие wParam=8 здесь не доказывает отсутствие language-событий:
контролируемого переключения для такого сравнения не было. App/probe exit 0,
fixture exit 1 по таймауту ручной активации, app `clean=true`.

Артефакты: `target/m1-shell-delivery-20260908-104454`.
В окончательный probe после этого прогона добавлены timestamp, обработка ошибок
stdout/защита FFI от unwind, проверка длительности и ограничение drain.

## Что проверять дальше

1. Повторить активную fixture одновременно с приложением на TRACE и shell_probe,
   сопоставить timestamp запроса, исходные Shell/TSF и чтение foreground.
2. Отдельно сравнить с ручным Win+Space в обычном Win32-приложении. Тест через
   WM_INPUTLANGCHANGEREQUEST не подменяет пользовательскую смену через оболочку.
3. Установить, почему в первом интервале нет также ForegroundChange при активации
   fixture, хотя очередной тик увидел новое окно и отключил fallback.
4. После локализации причины выбрать исправление и повторить 20/20 на выходе
   приложения. Только затем продолжать elevated/packaged/Terminal и NFR после смен.

Контракты проверены по Microsoft:
[RegisterShellHookWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registershellhookwindow)
описывает регистрацию, но не гарантирует в своей таблице HSHELL_LANGUAGE;
[TSF activation sink](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nn-msctf-itfinputprocessorprofileactivationsink)
задаёт способ подписки через ITfThreadMgr, не обещая все смены в чужих процессах.
Это согласуется с ранее открытыми рисками ADR-0013 и не доказывает причину само по себе.

Постоянный опрос обычных окон в этом расследовании не добавлен. Продуктовый код
остаётся на `47e51f3`; текущий результат — воспроизводимое наблюдение отказа и
диагностический инструмент. Дополнительный открытый блокер: WorkingSet 16,87 МиБ
при исходной цели 5–15 МБ. M1 не принят.

## Проверка диагностического кода

После последних правок: fmt-check, Clippy `--workspace --all-targets -D warnings`,
152 теста workspace/all-targets и `cargo +1.87.0 check --workspace --all-targets --locked`
прошли. Независимое read-only ревью проверило FFI, границы ожидания и RAII;
замечания закрыты. Двухсекундный native smoke окончательного probe: обе подписки
созданы, exit 0, stderr пуст. Аргумент длительности 0 отклонён с exit 1.
Это проверка диагностики, не исправление или повтор успешной доставки RU/EN.
