# 0020. Короткий аудиосигнал получает ограниченный запас тишины перед закрытием

Дата: 2026-09-08. Статус: accepted. Уточняет условие завершения из
[ADR-0018](0018-audio-device-playback-completion.md); владение STA, bounded
mailbox, работа по запросу и watchdog ADR-0016 сохраняются.

## Контекст

Пользователь подтвердил работу резервного чтения и сохранения галки, но не
слышит сигналы при реальных сменах. В законченном прогоне приложения 33 потока
достигли позиции 90 мс и закрылись без ошибки; выбран Realtek, mute=false.
Условия ADR-0018 недостаточно для слышимости на этой конфигурации.

Одинаковый PCM через один и тот же Burst: обычные 90 мс дали endpoint peak=0,
пользователь не слышал; те же 90 мс с секундой тишины после дали peak=0,469416,
пользователь слышал. Секунда тишины перед и после также слышна. Следовательно,
предварительный прогрев не требуется для этого воспроизведения сбоя.

Чистый повтор до исправления с разными запасами, два раза каждый: при 0 мс peak=0/0,000206;
при 25/50/100/200 мс — 0,469416–0,515781. Baseline всегда нулевой. Начальный
прогон с фоновым звуком исключён из обоснования. Артефакты:
`target/audio-tail-live-20260908-205436771`,
`target/audio-tail-sweep-20260908-210121032`.

После исправления T0..T1000 в audio_compare означают дополнительную тишину
поверх production-хвоста. T0 новой сборки не воспроизводит старый отрицательный
контроль; исторические результаты относятся к бинарнику до добавления минимума.

## Решение

При подготовке непустого сигнала дописывать нулевые PCM-кадры длительностью
`max(100 мс, GetStreamLatency)`, округляя число кадров вверх. 100 мс — запас
совместимости, выбранный по измеренному сбою и успешным меньшим значениям;
это не обещание Windows API и не точное измерение внутренней задержки драйвера.
Конкретный виновник внутри цепочки Windows/драйвера/эффектов пока не установлен.

Сами тон, громкость и начало PCM не меняются. Для 90-мс сигнала при нулевой
сообщённой задержке поток содержит 190 мс данных. Условие padding + clock
применяется ко всему буферу с запасом. Пустой startup probe не дополняется.
Постоянного потока или таймера в простое нет; Stop остаётся немедленно
доступным через сообщения. Новые подсказки сохраняются в существующем latest-slot.

## Альтернативы

- Оставить только clock: опровергнуто отрицательным контролем и слышимостью.
- Запас 1 с: полезный контроль, но слишком долго занимает текущий Burst и
  откладывает следующую подсказку.
- Запас 25 мс: прошёл два измерения, но выбран дополнительный запас до 100 мс
  для вариаций планирования/устройства; универсальность всё равно не доказана.
- Постоянный stream или объединение следующих подсказок внутри него: требует
  отдельного изменения lifecycle и ресурсных замеров; для найденного сбоя избыточно.
- Менять системные эффекты, глобальную громкость или режим драйвера: для
  исправления приложения не требуется и не следует из эксперимента.

## Последствия и проверка

После сигнала ресурсы заняты ещё минимум 100 мс; при частых сменах это может
добавить до 100 мс ожидания в существующей очереди. Создание/освобождение WASAPI
имеют собственные задержки, поэтому 190 мс не равно времени всего вызова.
Проверить сохранность PCM, нулевой конец, округление и большую сообщённую
latency, пустой probe, shutdown и серию через production worker. Повторная
проверка полного приложения пользователем нужна отдельно.

Microsoft описывает [GetPosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)
и [GetStreamLatency](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getstreamlatency);
добавочный запас — эмпирическая совместимость, а не требование этих контрактов.
