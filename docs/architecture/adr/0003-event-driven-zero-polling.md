# 0003. Событийная модель: нулевой поллинг в простое

Дата: 2026-07-03. Статус: accepted.

## Контекст

Требование «~0% CPU в простое» для резидентной утилиты. Все три ОС дают событийные механизмы для раскладки (shell hook + WinEvent + TSF / TIS-уведомления / XkbStateNotify, D-Bus), а для курсора — Raw Input / NSEvent monitors / XInput2. Но на Windows нет единого глобального события смены раскладки, и часть окон (elevated, UWP, консоль) события не отдаёт.

## Решение

Всё строится на подписках на события ОС. Таймеры и поллинг запрещены, кроме двух взводимых (armed) исключений, каждое из которых активно только пока строго необходимо:

1. Фолбэк-поллинг раскладки 500 мс на Windows — только пока передний план elevated/UWP/консоль.
2. Слежение за курсором (Raw Input и аналоги) — только пока бейдж видим; при скрытии подписка снимается.

Каждое новое исключение требует нового ADR и записи в overview.md.

## Рассмотренные альтернативы

- **Простой глобальный поллинг 100–200 мс** (так делают AutoHotkey-аналоги) — проще, но постоянные wake-up'ы: CPU, батарея, и это ровно то, чем продукт не хочет быть.
- **Только события, без фолбэка** — пропускает смену раскладки в elevated/UWP окнах; некорректность хуже редких взведённых опросов.

## Последствия

- (+) Честный «ноль» в Task Manager в простое — измеримое преимущество перед аналогами.
- (−) Оркестрация взведения/снятия подписок — отдельная логика ядра, покрывается тестами.
- (−) Windows-детекция — комбинация трёх источников с дедупликацией (ядро обязано дедуплицировать).
