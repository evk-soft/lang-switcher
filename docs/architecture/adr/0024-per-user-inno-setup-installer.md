# 0024. Распространение — установщик Inno Setup для текущего пользователя

Дата: 2026-09-09. Статус: accepted.

## Контекст

Первый публичный выпуск должен давать обычному пользователю Windows скачиваемый файл,
который ставится двумя щелчками, попадает в меню «Пуск» и корректно удаляется. До этого
решения существовала только сборка из исходников.

Дополнительные ограничения, заданные владельцем проекта: Windows 11 x64, установка без
прав администратора, сертификата для подписи кода нет.

Сравнение вариантов — [исследование от 2026-09-09](../../research/2026-09-09-alpha-localization.ru.md).

## Решение

- **Inno Setup 6.3+**, скрипт `packaging/windows/lang-switcher.iss`.
  [Лицензия](https://jrsoftware.org/files/is/license.txt) разрешает распространение
  созданных установщиков; уведомления штатного установщика сохраняются.
- `PrivilegesRequired=lowest` и `PrivilegesRequiredOverridesAllowed=` (пустое):
  запрос прав администратора невозможен ни по умолчанию, ни ключом командной строки.
  `{autopf}` при таких правах — `%LOCALAPPDATA%\Programs`.
- `AppId` — фиксированный GUID. Его нельзя менять: именно он отличает обновление
  существующей установки от появления второй записи в «Приложениях и возможностях».
- `AppMutex` совпадает с именем, которое приложение объявляет при старте
  (`switcher_windows::single_instance::APP_MUTEX_NAME`). Одно имя решает две задачи:
  вторая копия в сеансе не запускается, а установщик и деинсталлятор просят закрыть
  работающую копию вместо того, чтобы не суметь заменить занятый файл. Имя без префикса,
  то есть в пространстве имён сеанса: это верная область для установки в профиль
  пользователя, и при быстром переключении пользователей у каждого сеанса своя копия.
  Расхождение между `.iss` и константой ловит модульный тест, читающий сам `.iss`.
- Диагностические запуски с `--data-dir` mutex не берут: они изолированы явно и должны
  работать рядом с обычной копией.
- Автозапуск установщиком **не** включается — это остаётся галкой в трее. Но запись
  реестра, которую могло создать приложение, удаляется при деинсталляции: строка
  `[Registry]` с `ValueType: none` и `dontcreatekey` ничего не пишет при установке и
  срабатывает только на `uninsdeletevalue`.
- Конфиг и логи в `%APPDATA%` и `%LOCALAPPDATA%` не трогаются ни обновлением, ни
  удалением. Это данные пользователя; команда для их ручной очистки есть в руководстве.
- Сборка артефактов — один скрипт `packaging/build-release.ps1`, который вызывают и
  разработчик локально, и release-workflow: явная тройка `x86_64-pc-windows-msvc`,
  `cargo build --locked`, генерация `THIRD-PARTY-LICENSES.md`, portable-архив,
  установщик, `SHA256SUMS.txt`.
- Список сторонних лицензий генерирует `packaging/collect-licenses.py` из
  `cargo tree --edges normal` для Windows-тройки, то есть строго из того, что попадает в
  поставляемый бинарник. Сборочные и тестовые зависимости не распространяются и в список
  не входят. Ненулевой код возврата (нераспознанный крейт) обязан останавливать выпуск.
- `packaging/verify-install.ps1` выполняет установку, проверку и удаление без видимого
  рабочего стола, поэтому одинаково работает у разработчика и на раннере. Проверяется:
  тихая установка, совпадение версии установленного файла со собранным, запуск бинарника,
  совпадение контрольных сумм, а после удаления — исчезновение каталога, ярлыка и записи
  автозапуска при сохранности настроек. Джоба `package` в CI гоняет это на каждом PR:
  упаковка, которую проверяют только в момент тега, ломается в момент тега.
- Release-workflow останавливается на **черновике** выпуска. Неподписанную alpha сначала
  скачивает и ставит человек, и только потом она предлагается остальным.
- Подписи кода нет. Предупреждение SmartScreen и способ сверки SHA-256 описаны в
  release notes, README и руководстве по установке. Контрольные суммы — единственная
  проверка целостности, которая есть у неподписанного файла, поэтому они публикуются
  всегда.

## Рассмотренные альтернативы

- **WiX / MSI**: даёт групповые политики и корпоративное развёртывание, но требует учесть
  [условия maintenance fee](https://docs.firegiant.com/wix/osmf/) и заметно сложнее в
  упаковке. Для первой пользовательской alpha MSI не нужен.
- **NSIS**: сопоставим по возможностям, но у Inno из коробки готовы переводы мастера на
  четыре из шести наших языков и документированный контракт `AppMutex`.
- **Только portable-архив**: не даёт ни записи об удалении, ни ярлыка, ни защиты от
  установки поверх работающей копии. Архив остаётся, но как дополнение.
- **Установка для всех пользователей**: потребовала бы запроса прав администратора при
  каждой установке и обновлении ради программы, которая работает в сеансе одного
  пользователя.
- **`cargo-about` для лицензий**: ещё один незакреплённый инструмент, который нужно
  устанавливать и которому нужно доверять в выпускной джобе. Всё необходимое уже есть:
  `cargo tree` знает набор зависимостей, а реестр хранит тексты лицензий.
- **Публикация выпуска прямо из workflow**: удобно, но у неподписанного alpha-файла нет
  никакой проверки, кроме человека, который его скачал и поставил.

## Последствия

Появляется обязательство: `AppId` и имя mutex — часть публичного контракта. Смена
первого ломает обновление существующих установок, смена второго — согласование с
установщиком (это ловит тест).

Каждый PR теперь собирает установщик и прогоняет установку/удаление, что добавляет одну
джобу Windows-раннера к времени CI.

Пока нет подписи, каждый пользователь alpha проходит через предупреждение SmartScreen.
Это записано как ограничение выпуска, а не решено; появление сертификата потребует
отдельного ADR о том, где хранится ключ и как он попадает в CI.

Проверка на реальной чистой Windows выполняется человеком и дополняет то, чего hosted
runner не показывает: трей, оверлей, автозапуск после перезагрузки.
