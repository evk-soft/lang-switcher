# 0010. Per-Monitor-V2 включается рукописным манифестом через флаги линкера в `build.rs` бинарного крейта

Дата: 2026-08-25. Статус: accepted.

## Контекст

Вся геометрия оверлея (ADR-0005) опирается на предпосылку: `Point` — это физические экранные пиксели. Предпосылка верна только если процесс объявлен Per-Monitor-V2 DPI-aware. Иначе DPI-виртуализация подменяет и `GetCursorPos`, и рабочую область монитора, и бейдж тихо разъезжается на любом масштабе, отличном от 100 %.

Каркас объявил `embed-manifest` в `[workspace.dependencies]`, но: крейта нет ни в `Cargo.lock`, ни в локальном реестре (его никто не использует, поэтому он даже не резолвился), `build.rs` в репозитории отсутствует, а его API невозможно проверить по исходникам в этой сессии. Писать план или код по памяти о чужом API правила проекта запрещают.

Дополнительно обнаружена ошибка в карте файлов прежнего плана: `build.rs` был размещён в `switcher-windows`. Флаги линкера из build-скрипта применяются к бинарным целям **того же пакета**, поэтому манифест обязан встраиваться из build-скрипта пакета, который производит `lang-switcher.exe`, то есть `switcher-app`.

## Решение

**Манифест — рукописный XML в `crates/switcher-app/lang-switcher.manifest`**, встраиваемый как ресурс `RT_MANIFEST` с ID 1 через флаги линкера MSVC, выдаваемые из `crates/switcher-app/build.rs`:

```
/MANIFEST:EMBED
/MANIFESTINPUT:<абсолютный путь к lang-switcher.manifest>
```

Содержимое манифеста (проверено по Microsoft Learn, «Setting the default DPI awareness for a process»): узел `<asmv3:windowsSettings>` с `<dpiAware>true</dpiAware>` (схема SMI/2005, для совместимости со старыми ОС) и `<dpiAwareness>PerMonitorV2</dpiAwareness>` (схема SMI/2016). Per-Monitor-V2 через `<dpiAware>` выразить нельзя — только через `<dpiAwareness>`; Microsoft прямо рекомендует манифест и прямо не рекомендует задавать режим через API.

Build-скрипт гейтится по `CARGO_CFG_WINDOWS` и `CARGO_CFG_TARGET_ENV == "msvc"`, выдаёт `cargo::rerun-if-changed` на файл манифеста и ничего не делает на других платформах.

**Страховка в рантайме:** до создания любого HWND (установка обработчиков событий трея по ADR-0009 окон не создаёт и может идти раньше) процесс **сначала читает** свою фактическую awareness и только если она не Per-Monitor-V2 — вызывает `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`. Порядок именно такой, а не «сначала вызвать, потом прочитать»: успешный вызов сделал бы последующее чтение всегда положительным, и `warn!` перестал бы быть детектором отсутствующего манифеста. Ограничение задокументировано жёстко: «Once a window (an HWND) has been created in your process, changing the DPI awareness mode is no longer supported» — то есть вызов обязан быть раньше `TrayIconBuilder::build()` (он создаёт окно) и раньше создания оверлея.

**Проверка, а не вера:** результат этого чтения логируется — `debug!`, если awareness пришла из манифеста, и `warn!`, если её пришлось выставлять в рантайме. Один лог-факт вместо предположения, что манифест «наверное, встроился».

`embed-manifest` удаляется из `[workspace.dependencies]` (ADR-0008). Если в будущем окажется, что рукописный путь неудобен (например, для сборки под `*-windows-gnu`), крейт возвращается — но уже с проверенным по его документации API и новым ADR.

## Рассмотренные альтернативы

- **`embed-manifest` как основной путь.** Отклонено сейчас: API невозможно проверить в этой сессии, а описывать его по памяти правила запрещают. Решение не окончательное — это отказ от непроверенного, а не от крейта.
- **Только `SetProcessDpiAwarenessContext`, без манифеста.** Отклонено: Microsoft называет API-путь не рекомендованным, и он хрупок по порядку инициализации — любой ранний HWND (в том числе созданный зависимостью) навсегда фиксирует режим.
- **`SetProcessDpiAwareness` (shcore) или `SetProcessDPIAware`.** Отклонено: не дают Per-Monitor-V2; Learn называет `SetProcessDpiAwarenessContext` текущим рекомендованным API.
- **`build.rs` в `switcher-windows`.** Отклонено фактически: флаги линкера из build-скрипта действуют на бинарные цели своего пакета, а `lang-switcher.exe` производит `switcher-app`.
- **Путь через `.rc` + `windres`.** Отклонено: нужен только для `*-windows-gnu`, который проект не поддерживает; вернётся вместе с этой целью, если она появится.
- **Считать, что «манифест не нужен, у нас всё в физических пикселях».** Отклонено: без манифеста процесс получает виртуализованные координаты, и это ровно та ошибка, которую невозможно заметить на одном мониторе со 100 %.

## Последствия

- `crates/switcher-app` приобретает `build.rs` и артефакт `lang-switcher.manifest`; сборка под MSVC начинает зависеть от того, что путь до манифеста не превышает `MAX_PATH` (260 символов) — задокументированное ограничение `/MANIFESTINPUT`. Для путей вида `.claude/worktrees/...` это стоит держать в голове.
- Директивы build-скрипта сверены по Cargo Book из активного тулчейна (`share/doc/rust/html/cargo/reference/build-scripts.html`): `cargo::rustc-link-arg-bins=FLAG` — «Passes custom flags to a linker for binaries», `cargo::rustc-link-arg-examples=FLAG` — то же для примеров. Синтаксис с двойным двоеточием требует Cargo 1.77; MSRV проекта 1.87, поэтому используется он, а не устаревшая форма с одним двоеточием.
- Появляется наблюдаемый инвариант для smoke-чеклиста: строка лога с фактической DPI-awareness при старте; отсутствие `warn!` — доказательство, что манифест встроился.
- Все координатные утверждения ADR-0005 становятся законными. Если этот ADR когда-нибудь будет отменён, геометрия оверлея должна быть переосмыслена целиком.
- Проверка на mixed-DPI (бейдж на 100 % и 200 % мониторах) обязана выполняться на сборке **с** манифестом; прогон `cargo run` без него даст ложноуспешный результат на одном мониторе.
- **Smoke-примеры (`switcher-windows/examples/*`) манифеста не получают** — `cargo::rustc-link-arg-bins` действует на бинарные цели своего пакета, то есть только на `lang-switcher.exe`. Поэтому каждый пример обязан первой строкой вызывать `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` и логировать фактическую awareness; иначе прототип, снимающий главный риск проекта, снимал бы его на виртуализованных координатах. Побочная выгода: рантайм-страховка оказывается проверенной раньше, чем понадобится. Если когда-нибудь возникнет подозрение, что манифестный и рантайм-путь ведут себя по-разному, у примеров есть законная альтернатива — свой `build.rs` в `switcher-windows` с `cargo::rustc-link-arg-examples` и тем же `/MANIFESTINPUT`.
