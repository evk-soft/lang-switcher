# 0005. Геометрией бейджа владеет адаптер оверлея, DPI до ядра не доходит

Дата: 2026-08-25. Статус: accepted.

## Контекст

Ядро (`switcher-core`) уже реализовано и решает, **к чему** привязан бейдж: `Effect::ShowBadge { content, anchor }`, где `anchor` — `Caret(Point) | Cursor(Point) | Fixed`. Порт же принимал `Placement::At(Point) | PrimaryBottomRight`, а док-комментарий у `Effect::MoveBadge { pos }` гласил «runtime applies the offset». В результате три решения не имели владельца:

1. смещение от точки якоря до левого-верхнего угла бейджа;
2. прижатие бейджа к рабочей области, чтобы он не выехал за экран;
3. выбор монитора для фиксированного якоря на многомониторной конфигурации.

Отдельно висел DPI: `PlatformEvent::OverlayScaleChanged { dpi }` был объявлен, но не имел пары в `Engine::Event` — то есть попасть в ядро не мог физически, а `OverlayWindow::dpi_at(pos)` не вызывал никто. При этом overview.md требует пререндер под масштаб, обработку `WM_DPICHANGED` и пересчёт при пересечении мониторов.

## Решение

**Три вопроса — три владельца, без пересечений:**

- **Ядро** отвечает «к чему привязан бейдж» (`ResolvedAnchor`) и «что на нём написано» (`BadgeContent`). Оно не знает ни пикселей, ни DPI, ни мониторов.
- **Оболочка** (`switcher-app`) отвечает «сколько это в пикселях»: спрашивает у порта DPI будущего места и растеризует под него (ADR-0006).
- **Адаптер оверлея** отвечает «где именно на экране левый-верхний угол»: смещение, масштабирование смещения по DPI, выбор монитора для `Fixed`, прижатие к рабочей области.

Поверхность после решения:

```rust
// switcher-platform::events — ResolvedAnchor переезжает сюда (адаптер обязан его видеть),
// switcher_core::engine его ре-экспортирует. Placement УДАЛЯЕТСЯ.
pub enum ResolvedAnchor { Caret(Point), Cursor(Point), Fixed }

pub struct BadgeImage {
    pub width: u32,
    pub height: u32,
    pub bgra_premul: Vec<u8>,
    /// DPI, под который картинка отрисована (96 = 100%).
    pub dpi: u32,
}

pub trait OverlayWindow: Send {
    fn show(&self, image: &BadgeImage, anchor: ResolvedAnchor);
    fn move_to(&self, anchor: ResolvedAnchor);
    fn hide(&self);
    /// Эффективный DPI монитора, на который адаптер поставил бы `anchor`
    /// (включая монитор, который он сам выберет для `Fixed`).
    /// Отвечает синхронно на потоке вызывающего — без hop'а в поток оверлея.
    fn dpi_for(&self, anchor: ResolvedAnchor) -> u32;
}

// switcher-core::engine — MoveBadge несёт якорь, а не голую точку.
Effect::MoveBadge { anchor: ResolvedAnchor }
```

**DPI в ядро не идёт, и `Engine::Event` для него не добавляется.** `PlatformEvent::OverlayScaleChanged { dpi }` сохраняется, но его единственный потребитель — `switcher-app`: перерастеризовать и вызвать `show` заново. Диспетчер `PlatformEvent -> Option<engine::Event>` возвращает для него `None`.

**Обратная связь по масштабу — через сравнение, а не через сообщение.** Адаптер сравнивает `image.dpi` с DPI монитора, который он сам вывел; расхождение — единственный триггер `OverlayScaleChanged`. Отсюда: пересечение мониторов при слежении за курсором работает независимо от `WM_DPICHANGED`; цикл сходится за один шаг (при совпадении событие не отправляется); худший артефакт — один кадр в масштабе прошлого монитора, причём бейдж никогда не обрезан, потому что клампинг всегда идёт по фактическим `image.width/height`.

**Конкретика Windows (проверено по исходникам windows-0.62.2 и Microsoft Learn):**

- Кламп — по `MONITORINFO.rcWork` монитора, содержащего точку якоря (`MonitorFromPoint` + `MONITOR_DEFAULTTONEAREST`), а не по `rcMonitor` (бейдж уехал бы под панель задач) и не по объединению мониторов.
- `Fixed` — монитор активного окна (`MonitorFromWindow(GetForegroundWindow(), MONITOR_DEFAULTTOPRIMARY)`, при нулевом HWND — первичный), правый-нижний угол `rcWork` с отступом 16 логических px. На связке «ноутбук + внешний» первичный монитор — почти всегда не тот экран, поэтому политика «первичный» отвергнута.
- Зазоры: 12 логических px от курсора, 6 от каретки, 16 от края для `Fixed`; физический зазор = `logical * dpi / 96`.
- Позиция, размер и содержимое меняются одним вызовом `UpdateLayeredWindow` — промежуточного кадра нет; `SetWindowPos` используется только для перемещения без смены размера.
- `SWP_ASYNCWINDOWPOS` запрещён: он обходит правило «окном владеет его поток» и делает порядок show/move/hide ненаблюдаемым.

**Вся арифметика — в чистом модуле без `unsafe`:** `switcher-windows/src/overlay/geometry.rs` получает факты ОС аргументами (`WorkArea`, `dpi`, размер картинки, якорь) и покрывается табличными unit-тестами. `unsafe` остаётся только в «добыче фактов».

**Предусловие, без которого всё разъезжается:** `Point` — физические экранные пиксели, и это верно только при Per-Monitor-V2 awareness. Без манифеста DPI-виртуализация подменит и `GetCursorPos`, и `rcWork`. Процесс обязан быть PMv2 (манифест), а на старте — залогировать `warn!`, если фактическая awareness иная.

## Рассмотренные альтернативы

- **Смещение считает ядро (`ShowBadge { top_left: Point }`).** Отклонено: смещение физическое, зависит от DPI и от пиксельного размера бейджа — ядру пришлось бы знать оба, что убивает независимость от ОС и тестируемость на любой ОС.
- **Ядро получает топологию дисплеев событием и клампит само.** Отклонено: ядро превращается в мини-оконный менеджер (подключение мониторов, смена разрешения и масштаба), таблица тестов растёт кратно, пользователь не получает ничего.
- **`Engine::Event::ScaleChanged { dpi }` + `Effect::RerenderBadge`.** Отклонено: событие не порождает ни одного решения ядра — оно бы переслало число обратно как эффект. Шум в автомате.
- **Оставить `Placement` как отдельный платформенный тип и маппить `ResolvedAnchor -> Placement` в оболочке.** Отклонено: два типа об одном и том же, причём `Placement::At(Point)` теряет вид якоря, который адаптеру нужен для выбора смещения.
- **Оставить `Placement::PrimaryBottomRight`.** Отклонено: вшивает в словарь порта сразу две политики — «первичный монитор» и «правый-нижний угол».
- **Адаптер получает `Arc<dyn BadgeRenderer>` и тянет пиксели, когда узнал DPI.** Отклонено прямым правилом проекта: колбэк через границу потока, рендер исполнился бы на потоке оверлея.
- **Полагаться только на `WM_DPICHANGED`.** Отклонено как единственный источник: его доставка нашему `WS_EX_NOACTIVATE|WS_EX_TOOLWINDOW` окну при перемещении нами же документально не подтверждена; сравнение `image.dpi != monitor.dpi` не зависит ни от какого сообщения.

  > **Уточнение 2026-08-25 (задача 10, наблюдение, не документация).** Сообщение **приходит**, в том числе при нашем собственном `SetWindowPos`, и приходит *синхронно, реентрантно внутри этого вызова*. Решение это не отменяет, а усиливает: к моменту доставки `move_to` уже посчитал факты монитора и уже поставил бейдж, то есть источник, основанный на сообщении, отставал бы на кадр. Реентрантность добавляет неочевидное требование к реализации — состояние, которое трогает wndproc, не может быть тем же состоянием, которое в этот момент держит `&mut self`; поэтому инвалидация кэша DPI идёт через thread-local флаг, а не через `GWLP_USERDATA`.

## Последствия

- Ядро остаётся полностью тестируемым вне Windows: `switcher-core` не приобретает ни одного понятия о пикселях. Ломается ровно **один** тест (`pointer_moves_visible_tracking_badge`), и только потому, что `MoveBadge` теперь несёт `ResolvedAnchor::Cursor(pos)`. Ещё шесть тестов называют `ResolvedAnchor` коротким путём и продолжат компилироваться, пока `engine.rs` видит тип: тестовый модуль — дочерний и через `use super::*` видит даже приватный `use` родителя. Ре-экспорт (`pub use`) выбран сознательно и не ради тестов, а чтобы путь `switcher_core::engine::ResolvedAnchor` остался рабочим для оболочки.
- Форма `MoveBadge { anchor }` заранее выдерживает слежение за кареткой в M2 (`Event::CaretMoved` + `Effect::SetCaretTracking`) без изменения порта. Это главная причина не оставлять `MoveBadge { pos }`.
- `switcher-windows` требует фич `windows`: к `Win32_Foundation` и `Win32_UI_WindowsAndMessaging` добавляются `Win32_Graphics_Gdi` и `Win32_UI_HiDpi`. Неочевидное: `GetDpiForMonitor` требует **обе** фичи, `UpdateLayeredWindow` требует `Win32_Graphics_Gdi` вопреки своему расположению в `WindowsAndMessaging`, а `MONITORINFOF_PRIMARY` лежит в `WindowsAndMessaging`, не в `Gdi`.
- Появляется обязательство оболочки: держать `last_content`, `last_anchor`, `last_render_dpi` и игнорировать `OverlayScaleChanged { dpi }`, равный DPI последней отрисованной картинки (гасит гонку двух событий).
- `dpi_for` обязан отвечать без hop'а в поток оверлея, иначе главный цикл получит взаимную блокировку с обработкой сообщений оверлея. Это возможно потому, что `MonitorFromPoint`/`MonitorFromWindow`/`GetMonitorInfoW`/`GetDpiForMonitor`/`GetForegroundWindow` не принимают HWND нашего окна. **Потоковая аффинность этих вызовов выведена, а не процитирована** — проверяется тестом с двумя потоками (`overlay::tests::dpi_for_answers_from_a_foreign_thread`, зелёный с 2026-08-25: вызов не вешается, ответы совпадают) **плюс** smoke-прогоном, где `dpi_for` читает 144 и 96 на двух мониторах. Второе обязательно: `GetDpiForMonitor` зависит от awareness и DPI-неосведомлённому процессу отвечает 96 для любого монитора, что совпадает с фолбэком адаптера — без mixed-DPI наблюдения одно равенство было бы вхолостую.
- Кэш `HMONITOR -> dpi` внутри адаптера сбрасывается по `WM_DPICHANGED` и `WM_DISPLAYCHANGE`. Все вызовы происходят внутри обработки уже пришедшего события, поэтому ADR-0003 не нарушен.
- Чистая функция «кламп в рабочую область» будет продублирована в трёх адаптерах (M3/M4). Это осознанный non-goal M1: у macOS перевёрнутая ось Y, у X11 рабочая область доступна только через EWMH `_NET_WORKAREA`, так что общего кода меньше, чем кажется. Если дублирование окажется болезненным — заводится отдельный крейт `switcher-geometry` (новый ADR).
- Числа зазоров (12/6/16 логических px) и политика «`Fixed` = монитор активного окна» — продуктовые решения, зафиксированные здесь; проверяются глазами в smoke-чеклисте, а не тестом.
