# 0004. Оверлей на Windows — сырое layered-окно, без GUI-фреймворка

Дата: 2026-07-03. Статус: accepted.

## Контекст

Оверлей — самый рискованный компонент: должен быть поверх всех окон, не перехватывать клики и фокус, двигаться со скоростью курсора на mixed-DPI мониторах и ничего не стоить в простое. Аудит подтвердил: техника layered-окон стабильна десятилетиями («rock-solid»), тогда как webview/фреймворк-окна дают джиттер, RAM-пол и открытые баги прозрачности.

## Решение

Окно создаётся напрямую через windows-rs: `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST`. Бейджи (RU/EN × DPI-масштабы) пререндерены в premultiplied-ARGB (tiny-skia или вшитые PNG) один раз; на экран выводятся `UpdateLayeredWindow` **только при смене состояния** — ни рендер-цикла, ни swapchain. Перемещение — `SetWindowPos(SWP_NOACTIVATE|SWP_NOSIZE|SWP_NOZORDER)` по событиям Raw Input, коалесцированным до частоты кадров. Манифест Per-Monitor-V2; `WM_DPICHANGED` и пересечение мониторов обрабатываются явно.

## Рассмотренные альтернативы

- **egui/winit-окно** — тянет рендер-цикл и зависимость от winit 0.31 (mid-refactor); для статичного бейджа избыточно. egui остаётся для окна настроек.
- **DirectComposition + WS_EX_NOREDIRECTIONBITMAP** — путь для GPU-анимаций бейджа; отложено до реальной потребности (упростит анимации, усложнит код).
- **WH_MOUSE_LL для курсора** — отклонено: система молча снимает хук при превышении LowLevelHooksTimeout; Microsoft рекомендует Raw Input.

## Последствия

- (+) Idle-стоимость видимого бейджа — ноль (DWM сам композитит layered-окно); скрытого — буквально ноль.
- (+) Никаких зависимостей от GUI-фреймворков в критическом пути.
- (−) Ручной Win32-код с unsafe — компенсируется правилами скила `platform-api-work` и RAII-обёртками.
- (−) На macOS/Linux — свои техники (NSPanel / override-redirect+XShape), зафиксированы в overview.md, свои ADR при реализации M3/M4.
